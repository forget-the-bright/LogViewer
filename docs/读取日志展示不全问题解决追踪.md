## 一、问题现象（对应你日志查看工具出现的BUG）
**现象：日志初始加载只会吐出一行日志，剩下的数据一直卡住；只有产生新日志追加、或者主动断开/停止查看时，缓存里剩余日志才一次性全部推送出来。**

> 你工具里执行 `tail -F` / PowerShell `Get-Content -Wait` 获取日志流，底层命令本身很快把所有初始日志输出完毕，但Go后端没有及时转发给前端WebSocket。

## 二、原始代码错误逻辑（`procmgr.go` 旧实现）
核心代码结构简化：
```go
for {
    // ReadString('\n') 阻塞调用：没有新换行就一直等待
    line, err := br.ReadString('\n')
    // 收到一行，加入批量缓冲区
    batch.Add(line)
    // 【关键缺陷】只在读到一行之后，才检查定时是否需要flush
    if time.Since(lastFlush) > interval {
        flush(batch) // 批量推送到WebSocket
    }
}
```
### 缺陷拆解
1. `br.ReadString('\n')` **阻塞等待新行**；
2. 一批初始日志多条数据进入 `batch` 缓冲区；
3. 第一条日志触发一次检查，剩余日志进缓存；
4. 随后代码卡在 `ReadString` 等待新日志，**定时器检查逻辑永远无法执行**；
5. 40ms 的批量刷新计时器被“冻结”；
6. 直到有新日志产生、再次唤醒 `ReadString`，才会触发flush，一次性吐出积压数据。

简单一句话总结：**刷新判断逻辑和读取逻辑串行绑定，读取阻塞 = 刷新逻辑停滞。**

## 三、修复方案
### 修改点：`internal/procmgr/procmgr.go`
1. 缓冲区 `batch` 增加互斥锁 `sync.Mutex`，解决多goroutine并发读写竞争；
2. 单独启动一条独立goroutine，运行 `time.Ticker`，**不受ReadString阻塞影响**：
```go
ticker := time.NewTicker(40 * time.Millisecond)
go func() {
    for range ticker.C {
        flush() // 定时强制刷新缓冲区
    }
}()
```
- 读取循环继续收集日志写入batch；
- 独立定时器goroutine每隔40ms主动触发推送；
- 无论主读取循环是否阻塞，缓存内堆积日志都会按时推送给WebSocket前端。

## 六、结合你的项目提炼经验
针对你的跨平台日志工具：
1. 流式读取 + 批量缓冲场景，**不要把flush逻辑放在阻塞IO的同一个循环内**；
2. 日志流转发务必独立定时协程刷新缓冲区；
3. Windows PowerShell子进程极易出现僵尸进程，必须做进程生命周期管控；
4. 跨平台日志命令输出存在突发批量数据场景，缓冲区设计是关键坑点。
